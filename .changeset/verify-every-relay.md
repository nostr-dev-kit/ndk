Relays created after the NDK instance (added later, reached through the outbox model, or opened on demand) have their events verified again. The constructor built the pool before it set `validationRatioFn`, so those relays got the default ratio function bound to the relay instead of to NDK, which worked the ratio out as NaN: after ten validated events and the next ratio update, they never had another signature checked, whatever the options said. The configured relays never saw `initialValidationRatio`, `lowestValidationRatio` or `validationRatioFn` from the constructor options at all. Every relay now uses the options and the same ratio function. `lowestValidationRatio` now defaults to 1, so that out of the box every event from every relay is verified, as the documentation says and as the configured relays always did; set it below 1 to sample. A ratio that is not a finite number now means every event is checked.

`verifySignature` now rejects an event whose id is not the hash of its contents, or whose signature is not 128 hex characters, before it consults the cache of verified signatures, and a cached verification only answers for the same signature. The cache was keyed by the id an event claimed, so an event claiming the id of one verified in the last minute was accepted whatever its author, content or signature, and the synchronous path accepted a validly signed event under any id. Failed verifications are no longer cached, so a bad signature under a genuine event's id cannot get the genuine event rejected. The worker no longer hands one signature's result to another signature on the same event, and answers instead of throwing when it cannot parse a signature. With asynchronous verification, a subscription now drops an event that fails these checks at once instead of emitting it; an event with a well-formed but bad signature is still emitted first and reported once the worker answers, as before.
